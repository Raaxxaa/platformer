# RUSHBLADE — instructions for build chats

RUSHBLADE is a 2D speedrun action platformer (Dead Cells–style combat and loot, built for going fast). The person you're working with is the game's designer, **not a programmer**: explain things in plain words, show them screenshots and links, and don't ask them technical questions you can answer yourself.

## How this project is organized

There are two kinds of chats:

- **The design chat** decides what the game is. It owns `docs/GAME_PLAN.md`, `docs/spec/` and `docs/plans/`.
- **Build chats** (you) build exactly what those documents say: code, UI, art and sound.
- **An art chat** may run alongside a code chat. It follows the `ART*` plans in `docs/plans/` and only touches `tools/`, `public/assets/`, `docs/art/` and the `assets` script line in `package.json`. A code chat never edits those art files; it only loads them.

**Do not change the design.** If the spec is missing something or seems wrong:
1. Pick the simplest option that matches `docs/GAME_PLAN.md`.
2. Mark it in code: `// SPEC-GAP: <short question>`.
3. Add it to `docs/SPEC-GAPS.md` (create it if needed) with the file, the question, and what you chose.
4. Tell the user at the end of your work so they can take it to the design chat.

## Where things are

| Path | What |
|---|---|
| `docs/GAME_PLAN.md` | What the game is (the design, in plain words) |
| `docs/spec/` | **Exact rules and numbers.** Start with `docs/spec/00-README.md`; it has the tech stack, architecture and shared numbers |
| `docs/plans/` | Step-by-step build plans, one per milestone. **Do them in order.** Each task has files, tests and commands |
| `docs/SPEC-GAPS.md` | Questions for the design chat |
| `src/core/` | Pure TypeScript game rules. **No Phaser imports here, ever.** Deterministic, unit-tested |
| `src/data/` | Typed data tables (weapons, abilities, enemies, odds, prices) |
| `src/game/`, `src/ui/` | Phaser layer: scenes, sprites, HUD, menus. Draws core state, reads input. Never decides game rules |
| `tools/` | Python scripts that generate all art and sound into `public/assets/` |
| `tests/e2e/` | Playwright browser tests |

## Rules

- **Follow the current plan in `docs/plans/` task by task.** Write the test first, watch it fail, make it pass, commit. Don't skip ahead to later milestones.
- **All numbers come from the spec** and live in `src/core/tuning.ts` or `src/data/`. No magic numbers anywhere else.
- **The simulation runs at a fixed 120 ticks/second.** Game rules take an `InputState` per tick. The run timer counts ticks.
- **Randomness only through the seeded RNG** (`mulberry32`, one stream per system). Never `Math.random()` in `src/core/`.
- **Phaser is pinned to 4.2.1.** Most examples online are Phaser 3; check APIs against Phaser 4 types before using them.
- **Art and sound are generated by scripts in `tools/`.** Never hand-edit a generated PNG or WAV; change the script and re-run it. Every art script writes a preview image. Look at it with the Read tool before committing, and show it to the user when it's new.

## Commands

| Command | What it does |
|---|---|
| `npm install` | Install dependencies |
| `npm run dev` | Start the dev server (http://localhost:5173) |
| `npm run typecheck` | TypeScript check |
| `npm test` | Unit tests (Vitest) |
| `npm run build` | Typecheck + production build into `dist/` |
| `npm run test:e2e` | Build, serve, and run Playwright browser tests (takes screenshots into `test-results/`) |
| `npm run assets` | Re-generate art and sound from `tools/` |

Playwright uses the preinstalled Chromium at `/opt/pw-browsers/chromium` with the launch flag `--enable-unsafe-swiftshader`. **Never run `playwright install`.** Headless rendering is software-only: use it to check correctness and screenshots, not performance.

## Before you say something is done

1. `npm run typecheck`, `npm test` and `npm run build` all pass.
2. `npm run test:e2e` passes, and you **looked at the screenshots** with the Read tool.
3. Committed with a clear message, and pushed to your branch.
4. Tell the user what they can now see or play, in plain words, with a screenshot. Mention any SPEC-GAPs.

## Debugging help

- `?debug=1` in the URL shows hitboxes and exposes `window.__game` (core state, push inputs, step ticks). Playwright tests use it.
- If something about the cloud environment blocks you (network, missing tool), say exactly what, and keep going on what you can do.
